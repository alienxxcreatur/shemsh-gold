# نقشه مقدماتی سیستم طراحی شمش

وضعیت سند: `Draft / Design assumption`

تاریخ ایجاد: 20 Jul 2026

این سند نقشه کنترل‌شده برای شروع مقدماتی سیستم طراحی شمش است. هدف آن شروع رسمی مرحله ۷ نیست؛ هدف این است که زیرساخت‌های مستقل از برندبوک و مستقل از فلوهای نهایی، هم‌زمان با مرحله ۴ تا ۶ آماده شوند تا در مرحله ۷ سیستم طراحی از صفر شروع نشود.

## جایگاه این کار در پروژه

- **Observed fact:** طبق تصمیم D-084، Gate 3 با نتیجه `Sufficient to proceed` بسته شده و مرحله ۴ «معماری تجربه» فعال شده است.
- **Observed fact:** مرحله ۷ در نقشه راه رسمی هنوز مرحله فعال نیست.
- **Design assumption:** شروع یک مسیر سبک با عنوان `Design System Prep` پس از Gate 3 کم‌ریسک و مفید است، به شرطی که خروجی‌های آن `Draft` بمانند.
- **Risk:** اگر این مسیر به ساخت کتابخانه کامل، انتخاب نهایی برند، یا Stable کردن کامپوننت‌ها تبدیل شود، می‌تواند مرحله ۴ و ۵ را قاطی کند.
- **Business decision:** کیفیت بصری هدف باید آرام، دقیق، مالی و کمی لوکس باشد و طلایی کنترل‌شده استفاده شود.

## اصل راهبردی

سیستم طراحی در سه سطح جلو می‌رود:

1. **Design System Prep:** زیرساخت، قانون، معماری توکن، RTL، Light/Dark، QA و روش کار با Agentها.
2. **Design System in Use:** هم‌زمان با معماری تجربه، فلوها و وایرفریم‌ها، کامپوننت‌ها و Patternها با داده واقعی محصول تغذیه و تست می‌شوند.
3. **Official Design System:** در مرحله ۷، خروجی‌ها پاک‌سازی، مستند، Stable و برای تحویل رسمی آماده می‌شوند.

## آنچه الان امن است

- تعریف محدوده و Guardrailهای مسیر مقدماتی.
- تدوین Governance و مدل نگه‌داری.
- تعریف معماری توکن‌ها بدون مقدار نهایی برند.
- تعریف معماری Light/Dark.
- تعریف قواعد RTL، فارسی، اعداد و واحدهای مالی.
- تبدیل اصول طراحی به معیارهای قابل بررسی.
- تدوین دستورالعمل کار با Codex و Figma AI Agent.
- بازچینی فهرست کامپوننت‌ها براساس موج‌های Release اول.
- ساخت Draft چند کامپوننت پایه در Sandbox فیگما، نه Library اصلی.

## آنچه الان امن نیست

- اعلام شروع رسمی مرحله ۷.
- Stable کردن کامپوننت‌ها.
- انتخاب نهایی رنگ، فونت، Radius، Illustration یا Motion personality.
- طراحی نهایی کامپوننت‌های مالی وابسته به فلو.
- ساخت یک کتابخانه بزرگ قبل از کامل شدن معماری تجربه و فلوها.
- استفاده از برندبوک قدیمی به‌عنوان قانون نهایی ریدیزاین.
- اجازه دادن به Agent برای ساخت توکن، Naming یا Variant بدون بازبینی.

## وضعیت بلوغ خروجی‌ها

| وضعیت | معنی | کاربرد |
|---|---|---|
| `Draft` | قابل استفاده برای بحث و تست، نه منبع نهایی | سندهای مقدماتی و نمونه‌های Sandbox |
| `Design assumption` | فرض طراحی برچسب‌خورده تا رسیدن تصمیم یا تست | رنگ موقت، رفتار موقت، الگوی پیشنهادی |
| `Candidate` | گزینه‌ای که ممکن است وارد سیستم شود | کامپوننت یا توکن پیشنهادی |
| `Tested` | داخل وایرفریم یا پروتوتایپ تست شده، اما هنوز رسمی نیست | Patternهای مالی و Navigation |
| `Stable` | پذیرفته‌شده، مستند، تست‌شده و قابل استفاده رسمی | خروجی مرحله ۷ |
| `Deprecated` | نباید در کار جدید استفاده شود | اجزای جایگزین‌شده |

## نقشه قدم‌به‌قدم

### قدم ۱ — تعریف محدوده امن Prep

هدف: روشن کردن اینکه مسیر مقدماتی سیستم طراحی چه چیزی را جلو می‌برد و چه چیزی را عمداً عقب نگه می‌دارد.

خروجی:

- همین سند به‌عنوان نقطه شروع.
- بخش `Scope and guardrails` در همین سند.
- فهرست تصمیم‌هایی که هنوز نباید نهایی شوند.

نباید انجام شود:

- تغییر نقشه راه رسمی.
- تغییر وضعیت مرحله ۷ از «شروع نشده» به «در حال انجام».
- Stable اعلام کردن خروجی‌های مقدماتی.

معیار انجام:

- مرز Prep با مرحله ۷ روشن باشد.
- مسیر با مرحله ۴ تداخل نداشته باشد.
- خروجی‌های موقت برچسب وضعیت داشته باشند.
- موارد نیازمند تصمیم یا برندبوک جدا شده باشند.

### قدم ۲ — Governance و نگه‌داری

هدف: جلوگیری از رشد بی‌قاعده سیستم پیش از ساخت کامپوننت‌ها.

خروجی پیشنهادی:

- `07-design-system/governance.md`

موضوعات لازم:

- مالکیت تصمیم‌ها.
- وضعیت‌های `Draft`، `Candidate`، `Tested`، `Stable` و `Deprecated`.
- قانون اضافه کردن توکن.
- قانون اضافه کردن کامپوننت.
- قانون تغییر یا حذف Variant.
- روش ثبت تغییر.
- روش Audit دوره‌ای.
- معیار ورود از Sandbox به Library اصلی.

Definition of Done:

- هیچ توکن یا کامپوننت جدیدی بدون دلیل، وضعیت و مسیر بازبینی اضافه نشود.
- Agentها اجازه تصمیم‌گیری نهایی نداشته باشند.

### قدم ۵ — RTL، فارسی و عددهای مالی

### قدم ۶ — تبدیل اصول طراحی به معیار بررسی

Definition of Done:

- هر اصل حداقل چند معیار قابل بررسی داشته باشد.
- تصمیم‌های سلیقه‌ای با این معیارها قابل نقد باشند.

## Scope and guardrails برای قدم ۱

### محدوده این Prep

این مسیر فقط برای آماده‌سازی سیستم طراحی است و شامل طراحی نهایی UI محصول نیست.

در محدوده:

- اصول و معیارهای طراحی.
- Governance.
- توکن‌نام‌گذاری و معماری.
- Light/Dark architecture.
- RTL و عددهای مالی.
- Agent guidelines.
- Component inventory موج‌محور.
- Draft کامپوننت‌های پایه در Sandbox.

خارج از محدوده:

- UI نهایی صفحات.
- انتخاب نهایی برند.
- کامپوننت‌های مالی Stable.
- تصمیم‌های بیزینسی یا حقوقی.
- تغییر رسمی ترتیب مراحل پروژه.
- ساخت design system package یا repo جدا.

### Guardrailها

1. هیچ خروجی Prep بدون بازبینی انسانی `Stable` نمی‌شود.
2. هر مقدار وابسته به برندبوک با وضعیت `Design assumption` ثبت می‌شود.
3. هر مورد وابسته به فلو تا پایان مرحله مرتبط Draft می‌ماند.
4. هیچ Agent حق ساخت توکن یا Variant نهایی ندارد.
5. هر کامپوننت باید RTL و Light/Dark را از ابتدا در نظر بگیرد.
6. هر الگوی مالی باید به تصمیم محصول یا سؤال باز وصل باشد.
7. اگر قانون محصول باز است، UI فقط placeholder یا فرض برچسب‌خورده دارد.
8. برند قدیمی فقط ورودی تحقیق است، نه قانون نهایی.
9. سیستم طراحی نباید جای معماری تجربه یا فلوها تصمیم بگیرد.
10. تغییر مسیر رسمی پروژه فقط با تأیید مالک محصول و به‌روزرسانی منابع حقیقت انجام می‌شود.

### تصمیم‌هایی که هنوز نهایی نمی‌شوند

- رنگ‌های نهایی.
- فونت نهایی.
- Radius و Elevation نهایی.
- Motion personality نهایی.
- سبک Illustration و Photography.
- Navigation نهایی.
- Order summary، Receipt و Transaction timeline نهایی.
