# Governance سیستم طراحی شمش

وضعیت سند: `Draft / Design assumption`

تاریخ ایجاد: 20 Jul 2026

این سند قانون نگه‌داری و رشد کنترل‌شده سیستم طراحی شمش را تعریف می‌کند. هدف آن جلوگیری از توکن‌های پراکنده، کامپوننت‌های تکراری، Variantهای بی‌دلیل و تصمیم‌های زودهنگام است. این سند بخشی از `Design System Prep` است و شروع رسمی مرحله ۷ محسوب نمی‌شود.

## اصول Governance

1. سیستم طراحی از تصمیم‌های محصول تغذیه می‌شود، نه برعکس.
2. هر خروجی مقدماتی تا زمان تست و بازبینی، `Draft` یا `Design assumption` است.
3. هیچ چیز بدون دلیل، مالک، وضعیت و مسیر بازبینی به سیستم اضافه نمی‌شود.
4. Figma AI Agent و Codex می‌توانند پیشنهاد و اجرا کنند، اما تصمیم نهایی نمی‌گیرند.
5. کامپوننت مالی بدون فلو واقعی و Stateهای واقعی `Stable` نمی‌شود.
6. RTL و Light/Dark شرط پایه هر خروجی است، نه مرحله بعدی.
7. برندبوک، وقتی برسد، باید تا حد ممکن مقدار توکن‌ها را دقیق کند، نه معماری سیستم را از نو بسازد.

## وضعیت بلوغ

| وضعیت | معنی | چه کسی می‌تواند اعمال کند؟ | شرط خروج |
|---|---|---|---|
| `Draft` | ایده یا خروجی اولیه برای بحث و تست | طراح، Codex، Agent در Sandbox | بازبینی اولیه و اتصال به نیاز واقعی |
| `Design assumption` | فرض برچسب‌خورده تا رسیدن تصمیم، برندبوک یا تست | طراح یا Codex با ذکر دلیل | تأیید، اصلاح یا حذف پس از ورودی معتبر |
| `Candidate` | گزینه‌ای که می‌تواند وارد سیستم شود | طراح یا Codex پس از بررسی نیاز | تست در زمینه واقعی |
| `Tested` | در وایرفریم، پروتوتایپ یا سناریوی واقعی بررسی شده | طراح پس از QA یا بازبینی | تکمیل مستندات و رفع ایراد |
| `Stable` | قابل استفاده رسمی و تکرارشونده | فقط پس از بازبینی انسانی و معیارهای این سند | Audit دوره‌ای |
| `Deprecated` | نباید در کار جدید استفاده شود | طراح با ثبت جایگزین | حذف تدریجی از فایل‌ها و مستندات |

## قانون تغییر وضعیت

- `Draft` به `Candidate` فقط وقتی می‌رود که نیاز آن از مرحله محصول، فلو، وایرفریم یا کمبود مستند سیستم مشخص باشد.
- `Candidate` به `Tested` فقط وقتی می‌رود که حداقل در یک زمینه واقعی محصول تست شده باشد.
- `Tested` به `Stable` فقط وقتی می‌رود که RTL، Light/Dark، Stateها، محتوا و Accessibility بررسی شده باشند.
- هر خروجی وابسته به برندبوک تا رسیدن برندبوک `Design assumption` می‌ماند.
- هر خروجی وابسته به فلو تا تکمیل فلو یا وایرفریم مرتبط `Draft` یا `Candidate` می‌ماند.
- خروجی Agent هرگز مستقیم `Stable` نمی‌شود.

## قانون اضافه کردن توکن

توکن جدید فقط وقتی مجاز است که یکی از این شرایط برقرار باشد:

- نیاز تکرارشونده در حداقل دو زمینه یا کامپوننت دیده شود.
- یک نقش معنایی در سیستم وجود نداشته باشد.
- Accessibility یا Theme بدون توکن جدید آسیب ببیند.
- برندبوک یا تصمیم رسمی برند نیاز جدیدی ایجاد کند.
- کامپوننت مالی برای State واقعی به نقش معنایی تازه نیاز داشته باشد.

پیش از اضافه کردن توکن، باید بررسی شود:

- آیا توکن موجود کافی است؟
- آیا مشکل با Naming بهتر حل می‌شود؟
- آیا مقدار فقط تزئینی و یک‌بارمصرف است؟
- آیا Light و Dark هر دو مقدار لازم دارند؟
- آیا RTL یا فارسی روی این توکن اثر دارد؟

هر توکن باید این اطلاعات را داشته باشد:

| فیلد | توضیح |
|---|---|
| نام | براساس Naming سیستم |
| لایه | `primitive`، `semantic`، `component` یا `state` |
| نقش | چرا وجود دارد |
| مقدار Light | در صورت وجود |
| مقدار Dark | در صورت وجود |
| وضعیت | `Draft`، `Candidate`، `Tested` یا `Stable` |
| وابستگی | برندبوک، فلو، Accessibility یا تصمیم محصول |
| مثال استفاده | کجا مصرف می‌شود |
| ممنوعیت | کجا نباید استفاده شود |

## قانون اضافه کردن کامپوننت

کامپوننت جدید فقط وقتی مجاز است که:

- با کامپوننت موجود قابل ساخت نباشد.
- نیاز آن در فلو یا معماری تجربه مشخص باشد.
- فقط یک ترکیب محلی از چند کامپوننت ساده نباشد.
- رفتار، State یا Accessibility ویژه داشته باشد.
- تکرار آن در محصول محتمل باشد.

پیش از ساخت کامپوننت جدید، باید این پرسش‌ها پاسخ داده شوند:

- این کامپوننت چه Job یا فلو را پشتیبانی می‌کند؟
- آیا Pattern است یا Component؟
- آیا از کامپوننت‌های موجود قابل ترکیب است؟
- آیا به Variant نیاز دارد یا Property کافی است؟
- چه Stateهایی دارد؟
- چه محدودیت محتوایی دارد؟
- در RTL چه رفتاری دارد؟
- در Light/Dark چه تغییری دارد؟
- آیا هنوز به تصمیم محصول یا برند وابسته است؟

هر کامپوننت باید این اطلاعات را داشته باشد:

| فیلد | توضیح |
|---|---|
| نام | نام رسمی و یکتا |
| گروه | Action، Input، Data، Finance، Status، Navigation، Overlay، Trust، Physical یا گروه تازه |
| هدف | چرا وجود دارد |
| وابسته به موج | موج طراحی D-082 |
| وابسته به فلو | فلو یا صفحه مرتبط |
| Anatomy | اجزای داخلی |
| Variantها | فقط Variantهای ضروری |
| Stateها | Default، Focus، Loading، Error، Disabled و موارد خاص |
| RTL | رفتار و نمونه |
| Light/Dark | اتصال به توکن‌ها |
| Accessibility | Label، Focus، Keyboard، Screen Reader |
| Content constraints | طول متن، عدد، واحد، Empty، Error |
| وضعیت بلوغ | وضعیت فعلی |

## گیت اجباری ساخت و تأیید کامپوننت

طبق D-086، ساخت هر Component Draft باید با مسیر زیر انجام شود:

جزئیات عملیاتی، Artifactهای اجباری، Stop conditionها و روش Audit در `component-set-workflow-v1.0.md` مرجع اجرایی است.

1. `Pilot`: ابتدا فقط یک Variant نماینده با Anatomy، Token binding و Propertyهای اصلی ساخته شود.
2. `Technical preflight`: ساختار، Token binding، Auto Layout، Property، RTL و منبع Icon بررسی شوند.
3. `Visual QA`: خود Master Component و Instance آن جداگانه در Light و Dark با رندر یا Screenshot واقعی بررسی شوند.
4. `Stress test`: متن بلند فارسی، Hug/Fill، RTL، Focus، Disabled، Loading، Icon و اندازه‌های لازم تست شوند.
5. `Expand`: فقط پس از عبور Pilot از بررسی فنی و بصری، باقی Variantها ساخته شوند.
6. `Final dual audit`: Component Set کامل دوباره هم فنی و هم بصری بررسی شود و سپس برای Review انسانی ارائه شود.

قواعد این گیت:

- ساخت یک‌باره ماتریس کامل Variant پیش از تأیید Pilot ممنوع است.
- پاس‌شدن Token binding یا Audit برنامه‌ای به‌تنهایی کافی نیست.
- اگر داده‌ی resolved با رندر واقعی تناقض داشته باشد، خروجی بصری معیار پذیرش است و وضعیت Component باید `Needs revision` باشد.
- Paint متصل به Variable باید fallback منطبق با Mode فعال داشته باشد؛ fallback تصادفی مشکی، سفید یا مقدار خام نامرتبط مجاز نیست.
- هیچ Component بدون مشاهده Master و Instance در Light/Dark «تکمیل‌شده» اعلام نمی‌شود.
- تأیید نهایی بصری باید انسانی باشد؛ Self-audit سازنده جای Reviewer را نمی‌گیرد.

معیار عبور از گیت:

- Pilot در Master و Instance بدون اختلاف رندر شده باشد.
- تست‌های RTL، متن بلند، Theme، State، Icon و Layout پاس شده باشند.
- Component Set کامل بعد از توسعه دوباره Screenshot و Audit شده باشد.
- ایراد بصری شناخته‌شده باقی نمانده یا صریحاً با وضعیت `Needs revision` ثبت شده باشد.

## قانون Variant و Property

- Variant برای تفاوت معنایی یا رفتاری استفاده می‌شود، نه هر تفاوت ظاهری کوچک.
- Property برای تغییرات قابل کنترل مثل آیکن، Label، Size، State و Presence استفاده می‌شود.
- اگر تعداد Variantها زیاد شد، باید بررسی شود آیا کامپوننت اشتباه مدل شده است.
- Variant فقط برای پوشش سناریوی واقعی محصول ساخته می‌شود.
- Variant آزمایشی باید `Draft` بماند و وارد Library اصلی نشود.

## Sandbox تا Library

مسیر استاندارد هر خروجی:

1. `Sandbox / Draft`: ساخت اولیه، تست سریع، خروجی Agent یا نمونه دستی.
2. `Review`: بررسی Naming، توکن، RTL، Light/Dark، State و محتوا.
3. `Candidate`: قابل استفاده در وایرفریم یا پروتوتایپ.
4. `Tested`: تست‌شده در زمینه واقعی.
5. `Stable`: ورود به Library رسمی و مستندات.
6. `Deprecated`: جایگزینی یا حذف کنترل‌شده.

ورود به Library رسمی فقط وقتی مجاز است که:

- نام و ساختار نهایی باشند.
- توکن‌ها وصل باشند.
- Light و Dark نمونه داشته باشند.
- RTL نمونه داشته باشد.
- Stateهای الزامی پوشش داده شده باشند.
- Accessibility بررسی شده باشد.
- در `component-inventory.md` ثبت شده باشد.
- اگر مالی است، به فلو یا Pattern مرتبط وصل باشد.

## قانون Figma AI Agent

جزئیات اجرایی Prompt Packet، سطح ریسک، Stop condition، Proposal، Self-audit و Output manifest در `agent-guidelines.md` ثبت شده است. در صورت تعارض، Governance حاضر مرجع بالادستی است.

Agent مجاز است:

- در Sandbox نمونه بسازد.
- Variantهای مشخص‌شده در Prompt را بچیند.
- Documentation layout بسازد.
- نمونه‌های RTL و Light/Dark تولید کند.
- متن واقعی فارسی داخل نمونه‌ها قرار دهد.
- اصلاحات محدود و قابل بازبینی انجام دهد.

Agent مجاز نیست:

- خروجی را `Stable` اعلام کند.
- توکن نهایی بسازد.
- Naming جدید اختراع کند.
- کامپوننت موجود را Detach کند.
- Variant خارج از Prompt بسازد.
- کامپوننت را وارد Library اصلی کند.
- تصمیم برند یا محصول بگیرد.
- مقدار رنگ، فونت یا Radius را به‌عنوان نهایی تثبیت کند.

هر خروجی Agent باید با این چک‌لیست بازبینی شود:

- آیا در Sandbox ساخته شده؟
- آیا Naming مطابق سیستم است؟
- آیا از توکن استفاده کرده؟
- آیا مقدار خام یا پراکنده دارد؟
- آیا RTL درست است؟
- آیا Light و Dark دارد؟
- آیا متن فارسی واقعی دارد؟
- آیا Stateهای خواسته‌شده کامل‌اند؟
- آیا Duplicate یا Detach ایجاد شده؟
- آیا چیزی بدون اجازه Stable شده؟

## قانون Codex

قواعد اجرایی Codex برای جمع‌آوری Context، تدوین Prompt، Audit و توقف در تعارض یا کمبود تصمیم در `agent-guidelines.md` تکمیل شده است.

Codex می‌تواند:

- سند تولید کند.
- کمبودها را شناسایی کند.
- Prompt Packet بنویسد.
- خروجی Agent را Audit کند.
- تناقض با تصمیم‌های محصول یا سؤال‌های باز را ثبت کند.
- ساختار پیشنهادی بدهد.

Codex نباید:

- تصمیم محصول را بدون تأیید وارد Decision Log کند.
- فرض طراحی را واقعیت قطعی بنویسد.
- مرحله ۷ را بدون تأیید رسمی فعال اعلام کند.
- قانون باز محصول را در UI یا سند نهایی قطعی کند.
- تغییر ساختاری منابع حقیقت را بدون تأیید مالک محصول انجام دهد.

## Audit دوره‌ای

در پایان هر موج طراحی یا پس از چند خروجی Agent، Audit انجام می‌شود.

چک‌لیست Audit:

- توکن تکراری یا مقدار خام وجود ندارد.
- کامپوننت Duplicate یا Detach‌شده وارد Library نشده.
- Variantهای بدون استفاده حذف یا Deprecated شده‌اند.
- Light و Dark هر دو پوشش دارند.
- RTL و متن فارسی واقعی تست شده.
- Stateهای مالی فقط با رنگ منتقل نشده‌اند.
- کامپوننت مالی بدون فلو واقعی Stable نشده.
- ادعای اعتماد بدون Evidence وارد UI نشده.
- کامپوننت یا Pattern وابسته به سؤال باز، برچسب وضعیت دارد.
- مستندات و Figma با هم تناقض ندارند.
