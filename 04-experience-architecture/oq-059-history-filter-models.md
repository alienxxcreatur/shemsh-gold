# بسته تصمیم OQ-059 — فیلتر تاریخچه چندفلزی

آخرین به‌روزرسانی: ۱۸ مرداد ۱۴۰۵ / 9 Aug 2026

وضعیت: **قرارداد کامل U2 با D-124 تا D-128 قطعی — `Complete / Sufficient to prototype`**

دامنه: تاریخچه یکپارچه عملیات مالی و خدماتی؛ Release اول با طلا، نقره و مس؛ ظرفیت توسعه تا حدود ۱۶ فلز

## مسئله

تاریخچه شمش فقط معامله فلز نیست. خرید، فروش، واریز، برداشت، دریافت فیزیکی، سفارش هدف، هشدار، اقساط، هدیه و برخی رویدادهای رشد در محصول تعریف شده‌اند. پیش از طراحی نهایی فیلتر باید مشخص شود کدام‌یک واقعاً `Operation type` سطح اول‌اند و کدام موارد فقط status، subtype یا تاریخچه تخصصی یک سرویس هستند.

## تصمیم قطعی Taxonomy — D-124

- دسته‌های کلی `همه / معاملات / پول / خدمات` از پیشنهاد فعال کنار گذاشته شوند.
- در سطح اول، خود نوع عملیات‌ها به‌صورت Tab/Chip دیده شوند.
- زیادشدن تعداد Tabها و Scroll افقی در این تصمیم پذیرفته شده است.
- فیلتر فلز یک بُعد مستقل از نوع عملیات باشد و بعد از انتخاب هر Tab نیز قابل اعمال بماند.
- Label و ترتیب Operation tabها تأیید شده‌اند؛ `سفارش قیمت` یک Tab می‌ماند و پاداش زیر `واریز` گروه‌بندی می‌شود.
- Component و رفتار تعامل با D-126/D-128 بسته شده‌اند؛ Visual styling نهایی در وایرفریم و Design System اجرا و تست می‌شود.

## اصل استخراج Tab

یک Tab سطح اول باید یک عمل قابل‌فهم برای کاربر باشد، نه هر رکورد داخلی سیستم. بنابراین:

- جهت‌های پرتکرار و دارای معنای مستقل مثل `خرید` و `فروش` Tab جدا می‌گیرند.
- موجودیت‌های مستقل و تکرارشونده مثل `خرید اقساطی` و `پرداخت قسط` از هم جدا بررسی می‌شوند.
- statusهایی مثل موفق، ناموفق، لغوشده، منقضی، برگشتی و درحال آماده‌سازی Tab نوع عملیات نیستند.
- اصلاح مالی، برگشت و آزادسازی رزرو به Operation مبدأ متصل می‌مانند و Tab مستقل پیشنهادی ندارند.
- عملیات آینده یا حذف‌شده صرفاً برای کامل‌بودن Inventory ثبت می‌شوند و خودکار وارد UI Release اول نمی‌شوند.

## فهرست تأییدشده سطح اول

`همه / خرید / فروش / واریز / برداشت / دریافت فیزیکی / سفارش قیمت / هشدار قیمت / خرید قسطی / پرداخت قسط / صدور هدیه / دریافت هدیه`

این Taxonomy و ترتیب با D-124 قطعی است، اما قطعی‌شدن فهرست به معنی نهایی‌شدن Component و چیدمان UI نیست. پاداش معرفی رکوردی در تاریخچه عمومی دارد ولی از طریق Tab `واریز` پیدا می‌شود؛ status دعوت‌ها در صفحه تخصصی معرفی دوستان باقی می‌ماند.

## مواردی که عمداً Tab مستقل نشده‌اند

- `واریز کلان`: روش/زیرنوع واریز است.
- `سفارش اجراشده، لغوشده یا منقضی`: status سفارش قیمت است.
- `تسویه زودهنگام`: روش پایان‌دادن به قرارداد و subtype پرداخت قسط است.
- `لغو دریافت فیزیکی` و `برگشت وجه`: status/اثر جبرانی Operation اصلی‌اند.
- `اصلاح مالی`: رکورد حسابرسی متصل به Operation اصلی است.
- `انتقال`: قابلیت جاری محصول نیست.
- `پشتیبانی`: تاریخچه پرونده تخصصی دارد و پیشنهاد نشده Timeline مالی را شلوغ کند.

## مرز داده فیلتر فلز

- `operationType` و `assetId` دو بُعد مستقل Query هستند، اما مستقل‌بودن کنترل به معنی وجود `assetId` برای همه رکوردها نیست.
- خرید، فروش، دریافت فیزیکی، سفارش قیمت، هشدار، اقساط و هدیه رابطه مستقیم و قابل اثبات با یک `assetId` دارند.
- واریز، برداشت و پاداشِ گروه‌بندی‌شده زیر واریز ذاتاً ریالی‌اند و `assetId` ندارند؛ کیف تومان نیز میان فلزها تفکیک نشده است.
- Context شروع یک واریز از خرید طلا، مالکیت یا تخصیص وجه به طلا ایجاد نمی‌کند. ساختن `relatedAssetId` از این Context بدون قرارداد واقعی مالی، نسبت گمراه‌کننده می‌سازد.
- ترتیب فلزهای Release اول `طلا / نقره / مس` است و فلزهای بعدی از `AssetCatalog` می‌آیند.

## گزینه‌های رفتار ترکیب Operation × فلز

### R1 — تقاطع سخت و Empty

فلز فقط رکوردهای دارای همان `assetId` را برمی‌گرداند. بنابراین `واریز + طلا` و `برداشت + طلا` همیشه Empty هستند.

- مزیت: منطق Query کاملاً خالص و قابل پیش‌بینی است.
- ریسک: کنترل قابل استفاده به نظر می‌رسد اما برای Tabهای ریالی نتیجه مفیدی ندارد و Empty قابل پیش‌بینی تولید می‌کند.

### R2 — فیلتر مستقل با تعلیق آگاه از قابلیت — پیشنهاد

فیلتر فلز جای ثابتی دارد و انتخاب کاربر در Session حفظ می‌شود. در Tabهای دارای فلز، تقاطع سخت `operationType × assetId` اعمال می‌شود. در `واریز` و `برداشت`، کنترل فلز حذف یا Reset نمی‌شود اما با پیام «این نوع عملیات به فلز وابسته نیست» موقتاً غیرقابل اعمال است؛ با برگشت به یک Tab فلزی، انتخاب قبلی بازیابی می‌شود.

- مزیت: هیچ ارتباط مالی جعل نمی‌شود، Empty بی‌معنا تولید نمی‌شود و State کاربر از بین نمی‌رود.
- ملاحظه: «استقلال» در State و جای کنترل حفظ می‌شود، اما فیلتر در دو Operation فاقد بُعد فلز فعال نیست.
- الزام UX: حالت غیرقابل‌اعمال باید از Disabled معمولی متمایز و با متن روشن توضیح داده شود؛ صرفاً کاهش Opacity کافی نیست.

`Superseded by D-125`: مالک محصول تصریح کرد عملیات کیف تومان اصلاً فیلتر فلز نمی‌خواهند؛ بنابراین کنترل به‌جای Disabled/تعلیق، در Tabهای واریز و برداشت نمایش داده نمی‌شود.

### R3 — نسبت‌دادن Contextual

برای واریز یا برداشتِ شروع‌شده از یک فلو فلزی، `relatedAssetId` ثبت و فیلتر براساس `assetId OR relatedAssetId` اعمال می‌شود.

- مزیت: ترکیب‌هایی مثل `واریز + طلا` گاهی نتیجه دارند.
- ریسک: پول کیف تومانی قابل‌تعویض است؛ شروع از خرید طلا اثبات نمی‌کند واریز فقط برای طلا مصرف شده است. رکوردهای قدیمی و ورود مستقیم نیز رابطه ندارند. این مدل به‌عنوان قرارداد پایه توصیه نمی‌شود.

### R4 — نگه‌داشتن همه رکوردهای ریالی کنار فلز منتخب

در `همه + طلا`، عملیات طلایی همراه تمام واریزها و برداشت‌ها نمایش داده می‌شوند.

- مزیت: رکورد ریالی از Timeline ناپدید نمی‌شود.
- ریسک: فیلتر دیگر معنای دقیق ندارد؛ کاربر «طلا» انتخاب کرده اما رکوردهای نامرتبط می‌بیند. رد می‌شود.

## قرارداد قطعی عملیات ریالی — D-125

| Context | رفتار قطعی / باقی‌مانده |
|---|---|
| `همه + یک فلز` | فقط Operationهای دارای همان `assetId`؛ واریز، برداشت و پاداش ریالی نمایش داده نمی‌شوند |
| Tab فلزی + یک فلز | تقاطع سخت؛ مثال `خرید + نقره` فقط خریدهای نقره |
| `واریز` | همه واریزها و پاداش‌ها؛ کنترل فیلتر فلز نمایش داده نمی‌شود |
| `برداشت` | همه برداشت‌ها؛ کنترل فیلتر فلز نمایش داده نمی‌شود |
| تغییر از Tab فلزی به ریالی | `assetId` از Query فعال خارج می‌شود؛ حفظ آخرین انتخاب برای بازگشت یک رفتار UI پیشنهادی است |
| بازگشت به Tab فلزی | آخرین فلز معتبر بازیابی می‌شود — D-128 |
| ورود از جزئیات فلز | همان فلز روی `همه` یا Tab فلزی مرتبط اعمال می‌شود؛ ورود به Tab ریالی آن را به رابطه مالی تبدیل نمی‌کند |
| Deep Link / Back | Query اعمال‌شده، Tab و Scroll حفظ می‌شوند؛ Tab ریالی پارامتر `assetId` فعال ندارد |

`Business decision`: D-125 قرارداد داده را می‌بندد؛ R1 تا R4 فقط سابقه تحلیل‌اند و دیگر برای انتخاب باز نیستند.

## گزینه‌های UI پس از D-125

### U1 — دو ردیف مستقیم

ردیف اول Operation tabهاست. ردیف دوم Chipهای مستقیم `همه فلزها / طلا / نقره / مس` و کنترل‌های status/date است. در واریز و برداشت ردیف فلز حذف می‌شود.

- مزیت: سه فلز Release اول در یک نگاه و با یک Tap در دسترس‌اند.
- ریسک: با ۱۲ تا ۱۶ فلز یک ریل افقی دوم ساخته می‌شود، صفحه شلوغ و ارتفاع ناپایدار می‌شود و status/date به فضای دیگری نیاز دارند.

### U2 — ریل Operation + انتخاب‌گر فشرده فلز + فیلترها — منتخب D-126

ردیف اول Operation tabهاست. ردیف دوم برای Operationهای فلزی یک کنترل مستقل `فلز: همه فلزها` و یک دکمه `فیلترها` برای status/date دارد. در واریز/برداشت فقط `فیلترها` باقی می‌ماند. انتخاب‌گر فلز Sheet فهرستی باز می‌کند و از آستانه ۷ فلز Search دارد.

- مزیت: استقلال فلز واضح می‌ماند، فقط یک ریل افقی وجود دارد و مدل از ۳ تا ۱۶ فلز بدون تغییر Component مقیاس می‌گیرد.
- مزیت: `فیلترها` می‌تواند شمارنده status/date فعال داشته باشد و Summary فیلتر بدون شلوغی باقی بماند.
- ملاحظه: انتخاب فلز یک Tap بیشتر از U1 نیاز دارد.

`Business decision`: U2 با D-126 تأیید شده و مبنای وایرفریم است. U1 و U3 فقط سابقه مقایسه‌اند و دیگر گزینه فعال نیستند.

### U3 — یک دکمه فیلتر مشترک

پس از Operation tabها فقط `فیلترها` دیده می‌شود و فلز، status و تاریخ همگی داخل یک Sheet هستند. در واریز/برداشت بخش فلز از Sheet حذف می‌شود.

- مزیت: کم‌ارتفاع‌ترین و ساده‌ترین سطح صفحه.
- ریسک: فلز به‌عنوان بُعد مستقل دیده نمی‌شود و تشخیص فیلتر فعال بدون بازکردن Sheet ضعیف‌تر است؛ با خواسته صریح مالک محصول درباره استقلال فلز هم‌راستایی کمتری دارد.

## قرارداد پایه قطعی U2 — D-126

- Operation rail تنها Scroll افقی صفحه است؛ Swipe محتوای Timeline بین Tabها فعال نمی‌شود تا با Back و ژست سیستم تداخل نکند.
- Tab انتخاب‌شده با ورود/Back به داخل View Scroll می‌شود و Active state علاوه بر رنگ Indicator صریح دارد.
- Target لمسی حداقل ۴۴×۴۴px و فاصله کنترل‌ها حداقل ۸px است.
- `فلز: ...` یک کنترل مستقل از Operation و `فیلترها` است.
- `فیلترها` محل status/date است؛ قرارداد دقیق آن با D-128 بسته شده است.
- در واریز/برداشت، کنترل فلز Render نمی‌شود و فقط `فیلترها` باقی می‌ماند — D-125.

`Business decision`: ساختار بالا قطعی است. حداقل Target لمسی ۴۴×۴۴px، فاصله ۸px، Active state صریح و پرهیز از Swipe متداخل قواعد کیفی اجرای همین مدل‌اند.

## تصمیم‌های بسته‌شده و کار باقی‌مانده

بسته‌شده با D-124:

- فهرست و ترتیب ۱۲ کنترل سطح اول تأیید شد.
- `سفارش قیمت` یک Tab مشترک ماند.
- `خرید قسطی / پرداخت قسط` و `صدور هدیه / دریافت هدیه` جدا ماندند.
- پاداش Tab مستقل ندارد و زیر `واریز` گروه‌بندی می‌شود.

کار باقی‌مانده OQ-059: ندارد. دامنه فعال‌بودن هر فیچر برای هر فلز، تصمیم این بسته نیست و در OQ-054 پیگیری می‌شود.
