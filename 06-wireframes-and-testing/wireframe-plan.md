# برنامه وایرفریم و پروتوتایپ

## ترتیب اجرایی چندفلزی — D-131

> موج‌های قدیمی حذف نشده‌اند؛ خروجی‌های آن‌ها به‌عنوان شواهد Reuse نگه داشته شده‌اند. از این نسخه، شناسه `MM-W*` ترتیب ساخت تجربه هدف چندفلزی را مشخص می‌کند. `MM-W1` و `MM-W3` طبق D-130 هم‌زمان آغاز می‌شوند و OQ-054 موازی ادامه دارد.

### مبنای محاسبه درصد

درصد زیر فقط **پیشرفت ساخت وایرفریم هدف** است؛ کامل‌بودن سند فلو یا بسته آمادگی به‌تنهایی پیشرفت ساخت محسوب نمی‌شود. هر خروجی لازم یکی از این امتیازها را می‌گیرد و درصد موج میانگین همان خروجی‌هاست:

| امتیاز | تعریف |
|---:|---|
| ۰٪ | هیچ وایرفریم قابل‌استفاده‌ای وجود ندارد |
| ۲۵٪ | فقط ورودی، Placeholder یا تکه ساختاری مرتبط در وایرفریم قبلی وجود دارد |
| ۵۰٪ | معادل تک‌فلزی/قدیمی قابل Reuse وجود دارد، اما نسخه هدف چندفلزی ساخته نشده است |
| ۷۵٪ | ساختار هدف ساخته شده، اما State coverage، اتصال یا QA/Review کامل نیست |
| ۱۰۰٪ | وایرفریم هدف با Stateهای اجباری ساخته، QA و Review شده است |

## Gate اجباری پیش از ساخت همه وایرفریم‌ها

برای هر فلو یا خوشه فلو، یک بسته آمادگی براساس `flow-readiness-pack-template.md` لازم است. این Gate فقط چک‌لیست UI نیست و باید منابع قواعد، eligibility، قرارداد رفتاری، قرارداد Field/Component، State/Recovery، دسترس‌پذیری و پیشنهادهای پیش‌دستانه را پوشش دهد.

- مسئولیت طراح/دستیار: انتخاب الگوی استاندارد، کشف شکاف و حالت لبه، ارائه توصیه، ساخت ماتریس حالت و QA قبل از تحویل.
- مسئولیت مالک محصول: تأیید سیاست بیزینسی، حقوقی یا trade-off واقعی؛ نه اصلاح جزءبه‌جزء استانداردهای پایه.
- قانون توقف: `Draft` و `Needs decision` مجوز ساخت نیستند؛ فقط `Sufficient to prototype` مجوز ساخت یا بازسازی اساسی است.

## Gate اجباری پس از ساخت و پیش از Review

پیش از ارائه هر فایل موبایل به مالک محصول، برای هر Screen و Field این کنترل‌ها باید صریحاً پاسخ داده و تست شوند:

- Context ورود: کپی فقط وقتی خرید، فروش یا مقصد دیگری را نام می‌برد که همان Context در Prototype فعال باشد.
- مقصد خروج: Back، ×، «بعداً» و Success هرکدام باید مقصد نام‌دار داشته باشند؛ کنترل بدون مقصد مشخص نمایش داده نشود.
- نوع ورودی موبایل: تاریخ، مبلغ، OTP و انتخاب‌ها پیش از ساخت به Picker/Keyboard/Drawer مناسب نگاشت شوند؛ Text Input پیش‌فرض نیست.
- Auth: تشخیص حساب پس از موبایل، ورود رمزمحور، OTP فقط برای Signup/Migration/Recovery، Signup متصل به KYC و مقصد خانه برای سایر مسیرها تست شوند.
- Password: حداقل ۸ کاراکتر با حرف انگلیسی و عدد، آیکن چشم، Autofill/Paste، Error نزدیک فیلد و بازیابی با OTP تست شوند؛ سقف فنی در UI نوشته نشود.
- OTP: رقم ششم Auto-submit، کد نامعتبر/منقضی پاک، اعتبار سه دقیقه و Resend پس از ۶۰ ثانیه جدا، Autofill/Paste حفظ شود.
- Feedback: Loading و Success/Error قابل‌مشاهده باشند؛ اگر مقصد معلوم است Success فقط بازخورد گذرا باشد و CTA اضافه نسازد.
- Recovery: Retry، Resend، Cancel و بازگشت بدون پاک‌شدن داده‌های نامرتبط تست شوند.
- State Matrix: Default، Focus، Filled، Invalid، Expired، Loading، Success، Service Error و خروج داوطلبانه روی خود Prototype اجرا شوند.
