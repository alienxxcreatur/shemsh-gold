# قرارداد ساختار خانواده صفحات — نسخه ۰.۱

تاریخ: ۱۹ اوت ۲۰۲۶  
دامنه: Baseline وایرفریم پیش از استخراج Patternهای بایننس  
بسته: `PB-4 — قراردادهای ساختاری مشترک`

## اصل پایه

- `Business decision` — ساختار و رفتار خانواده صفحات مشترک است؛ داده و فیلدهای هر عملیات از Schema همان نوع می‌آید.
- `Observed fact` — Header، CTA ثابت، Overlay، State summary و Operation detail در Prototype مرجع Renderer یا Mount مرکزی دارند.
- `Design assumption` — Visual treatment نهایی این قرارداد در مرحله بایننس/High-fidelity تعیین می‌شود؛ این سند درباره ترتیب، معنا و رفتار است، نه رنگ و Radius نهایی.
- `Risk` — یک «رسید عمومی» با فیلدهای ثابت برای همه عملیات ممنوع است؛ اشتراک باید در Composition باشد، نه در اطلاعات نامرتبط.

## ۱. Page shell و Header

| خانواده | ساختار الزامی | Back / خروج |
|---|---|---|
| Root | Header سه Slot، عنوان مرکزی، حساب در چپ، اعلان در راست، Bottom nav | تغییر Tab، نه Back |
| Subpage | Header سه Slot، عنوان مرکزی، Back در راست، بدون Bottom nav | بازگشت به Snapshot مبدأ با Draft و Scroll |
| Entry معامله | Header بصری حذف، عنوان `sr-only`، Tab فلز در ابتدای محتوا | Bottom nav؛ اگر از Context دیگری آمده باشد Back منطقی حفظ شود |
| Processing | عنوان/وضعیت زنده، بدون CTA تکرار Submit | Callback معتبر یا مسیر پیگیری؛ Callback قدیمی بعد از خروج بی‌اثر |
| Terminal قطعی | Status + اطلاعات همان عملیات + CTA مقصد پایدار | نباید به Processing قبلی برگردد |

تمام صفحه‌های اصلی از `setChrome()` استفاده می‌کنند. ساخت Header مستقل داخل Renderer تازه مجاز نیست، مگر فایل تخصصی Auth/KYC که Header داخلی خودش را دارد.

## ۲. فرم‌ها

ترتیب استاندارد هر فرم:

1. Context ضروری مانند موجودی یا محدودیت؛
2. `label` متصل به Control؛
3. Input/Selector با واحد یا Affordance؛
4. Helper ثابت یا Error همان فیلد؛
5. Preview/Submit به‌عنوان CTA نهایی صفحه.

قرارداد Error:

- `aria-invalid` روی Control؛
- `aria-describedby` به Helper خطا؛
- خطا دارای `role="alert"` و کنار همان فیلد؛
- Draft پس از خطا و Back حفظ می‌شود؛
- CTA تا معتبرشدن ورودی واقعاً `disabled` است، نه ظاهراً بی‌عمل.

فرم‌های واریز، برداشت، کارت بانکی، رمز و دریافت هدیه با این قرارداد همگام شده‌اند. فرم Auth/KYC همین قرارداد را در فایل تخصصی اجرا می‌کند.

## ۳. Bottom Sheet و Dialog

### Bottom Sheet

- برای انتخاب، توضیح تکمیلی یا اقدام Contextual استفاده می‌شود؛ نه مقصد تمام‌صفحه پیچیده.
- Wrapper مرکزی: Scrim + `role="dialog"` + `aria-modal="true"` + عنوان + Handle + دکمه بستن.
- خروج: Close، لمس Scrim و `Escape`؛ Focus به Trigger برمی‌گردد.
- اگر تصمیم نهایی دارد، CTA در `sheet-footer` پایین Sheet می‌ماند.
- فهرست انتخابی بدون Submit اضافی می‌تواند با انتخاب یک Row بسته شود.

### Dialog

- فقط برای تصمیم کوتاه و متمرکز که خروجی دوشاخه دارد.
- `alertdialog` برای تغییر مخرب Draft؛ عنوان و توضیح با ARIA متصل‌اند.
- Primary نتیجه تغییر را می‌گوید؛ Secondary ادامه وضعیت فعلی/لغو را روشن می‌کند.
- لمس Scrim تصمیم را ضمنی تأیید یا رد نمی‌کند.

## ۴. Empty، Loading و Error State

| State | محتوای لازم | اقدام |
|---|---|---|
| Empty | چه چیزی وجود ندارد + این وضعیت چه معنایی ندارد | نزدیک‌ترین اقدام ممکن یا تغییر Filter موجود |
| Loading | چه چیزی در حال انجام است + جلوگیری از Submit تکراری | معمولاً بدون CTA؛ در Loading طولانی مسیر پیگیری |
| Pre-submit error | علت قابل اصلاح نزدیک فیلد | اصلاح همان Draft |
| Recorded failed | Status + داده Attempt موجود + اثر موجودی + Recovery | Retry امن، History یا Support Contextual |
| Unknown | عدم قطعیت صریح + منع تکرار + روش پیگیری | History/Support، نه Submit دوباره |
| Unavailable | قابلیت فعلاً در دسترس نیست + جایگزین واقعی | تغییر انتخاب یا بازگشت |

State مستقل نباید اطلاعات Tracking اختراع کند. Tracking فقط وقتی Record ثبت‌شده وجود دارد نمایش داده می‌شود.

## ۵. CTA ثابت

- فقط `action-stack` نهایی فرزند مستقیم صفحه یا پنل مجاز به انتقال به `page-action-root` است.
- CTA Contextual داخل Card، Filter، Picker و Dialog در جای محتوایی خود می‌ماند.
- صفحه حداکثر یک Primary نهایی دارد؛ Secondary برای ویرایش، بازگشت یا مقصد مکمل واقعی است.
- CTA ثابت Main را نمی‌پوشاند و Safe area را رعایت می‌کند.
- Processing CTA Submit ندارد؛ Terminal CTA به مقصد پایدار می‌رود.

## ۶. جزئیات عملیات

ترتیب Composition مشترک:

1. Status؛
2. عنوان نوع‌محور؛
3. توضیح فقط در حالت لازم؛
4. Numeric/Object anchor مرتبط؛
5. بخش «اطلاعات [نوع عملیات]» با فیلدهای Schema؛
6. زمان و کد پیگیری در صورت وجود؛
7. وضعیت موجودی/راه ادامه فقط وقتی از عنوان و Anchor قابل فهم نیست؛
8. اقدام‌های Contextual.

### Schema نوع‌محور

| نوع | Anchor | فیلدهای اختصاصی |
|---|---|---|
| خرید | وزن خرید | فلز، وزن، مبلغ، نرخ ثبت‌شده و روش پرداخت در صورت وجود |
| فروش | مبلغ دریافتی | فلز، وزن فروخته‌شده، مبلغ، نرخ و مقصد تسویه |
| تلاش معامله | مبلغ تلاش | فلز، جهت و مبلغ تلاش؛ نه فیلد عمومی «شرح» |
| واریز | مبلغ واریز | روش واریز |
| برداشت | مبلغ برداشت | مقصد بانکی |
| دریافت فیزیکی | مقدار فیزیکی | فلز، مقدار و ترکیب محصول |
| هشدار | قیمت هدف | فلز و شرط هشدار؛ بدون اثر مالی ساختگی |
| سفارش قیمت | مبلغ سفارش | فلز، مبلغ و جهت سفارش |
| خرید اقساطی | مبلغ قرارداد | فلز و دوره قرارداد |
| پرداخت قسط | مبلغ پرداخت‌شده در موفق؛ مبلغ قسط در Failed/Pending | فلز قرارداد، مبلغ و شماره قسط |
| صدور هدیه | مقدار هدیه | فلز و روش تحویل |
| دریافت موفق هدیه | مقدار دریافت‌شده | فلز، مقدار و اثر دریافت |
| تلاش دریافت هدیه | مقدار هدیه | فلز، مقدار و روش دریافت؛ نباید «دریافت‌شده» بنویسد |
| پاداش معرفی | اعتبار ثبت‌شده | نوع اعتبار، مقدار و شرایط استفاده |

Fallback عمومی فقط برای نوع واقعاً ناشناخته مجاز است و نباید برای عملیات شناخته‌شده استفاده شود.

## ۷. موارد Business-gated

- `Open question` — فیلدهای لغو/تسویه دریافت فیزیکی تا تصمیم D-206 نهایی نیستند.
- `Open question` — داده رزرو/لغو/اجرای سفارش قیمت تا تصمیم D-206 نهایی نیست.
- `Open question` — کارمزد، جریمه، فسخ و وثیقه اقساط تا تصمیم D-206 نهایی نیست.
- `Open question` — انقضا/تحویل هدیه و Case پشتیبانی تا تصمیم D-206 نهایی نیست.

این موارد می‌توانند از Composition مشترک استفاده کنند، اما Row و CTA حل‌نشده نباید از Pattern بایننس یا حدس طراحی استخراج شود.

## Gate PB-4

`Sufficient to proceed`

- Header، Form، Sheet، Dialog، State و Fixed CTA قرارداد مشترک دارند.
- عملیات شناخته‌شده به Schema اختصاصی متصل‌اند.
- Labelهای نادرست «پرداخت‌شده/دریافت‌شده» در Failed/Expired حذف شده‌اند.
- تصمیم‌های باز بیزینس از قرارداد ساختاری جدا مانده‌اند.
- QA بصری، Responsive، Focus و Screen reader نماینده در PB-5 انجام می‌شود.
